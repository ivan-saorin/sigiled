## Binding design

The browser driver represents the actual signed-in human. It obtains a compatible Authentik operator access token via authorization-code + PKCE and keeps access/refresh tokens server-side. That same caller JWT will be forwarded to SDE/ADHD/Genie/memory; do not mint service credentials or substitute sigiled-claude, the bootstrap bearer or a shared API token. Existing machine Actor authentication continues unchanged.

Use an explicitly configured browser origin allowlist for Sigil and memory. Both will share this session contract but each has a host-only cookie and separate login callback; Authentik provides SSO. This browser module can live in sigiledd, with future edge routes sending the two sites' browser paths here while existing machine service routes remain unchanged. Do not assume edge cookie auth implies a usable downstream JWT.

## Required behavior

- Browser feature off unless configured/enabled. Validate configuration on startup; fail closed on partial/insecure configuration. Production origins/endpoints must use HTTPS with exact hosts, no userinfo/fragments/query or arbitrary redirects. Any HTTP exception must be explicit test-only or loopback development-only. Use trusted fixed issuer discovery/config; never fetch issuer metadata from client input.
- Implement login start, OAuth callback, session inspection, logout and a narrow authenticated browser API foundation. Exact `/browser/...` routes documented. PKCE S256, cryptographically random state/nonce/verifier/cookie session IDs, bounded one-use login transactions, state bound to an independent host-only login cookie, finite expiry, and nonce/audience/exact-issuer/signature/expiry validation for ID token. Validate the operator access token through the existing Authentik JWT/Actor policy, additionally bind it to the configured browser issuer. Confirm same subject identity rather than trusting arbitrary display text. Tokens never enter localStorage, response JSON, links, logs or error bodies.
- The post-login cookie is `__Host-sigil_session`, Secure, HttpOnly, SameSite=Lax, Path=/ and no Domain; rotate at login, bind server record to exact origin and actor, enforce idle/absolute expiry. Store tokens only server-side. An in-memory browser session store is acceptable for this stage if restart logs out cleanly; explicitly document it. Bound store size and prune expired login/session entries. No unauthenticated session fixation. Login and callback error paths leave no usable cookie/credential behind.
- Validate both CSRF token and exact Origin on all cookie-authenticated mutations, including logout and later action routes. Session inspection returns only safe actor/capability/expiry/configured-feature information and a CSRF token. Safe GET reads do not open workspaces or trigger inference. Do not put machine endpoints behind browser cookie auth or silently widen their authorization.
- Refresh access tokens server-side if a refresh token was explicitly issued; serialize refresh per browser session to prevent rotation races. Revalidate returned identity/issuer/role and revoke session on invalid/rejected refresh. Do not extend the absolute browser session lifetime indefinitely. If refresh is unavailable/expired, return a typed 401 requiring login; do not silently replay arbitrary mutations or replace the caller token.
- Preserve logout/expiry across concurrent refresh: a late token response must never recreate a removed session or extend its original absolute lifetime. If a refresh request is cancelled or its result is uncertain after the provider may have rotated the token, do not retry the old refresh credential as though nothing happened; either retain an owned completion path that safely updates the still-live session or revoke and require login. Test these races with the fake IdP.
- Provide a narrow reusable server-side browser context/extractor carrying actor + compatible access token for future adapters. No generic arbitrary URL proxy. Never expose raw `sessions::open` JSON or skill-render endpoints to cookie clients. Browser-opened workspace tokens remain in core custody and will be projected safely in C2.
- Include endpoint-specific request size/time limits and no credential-bearing tracing. Callback authorization codes must not appear in logs. Login redirects accept only validated same-origin return paths; disallow protocol-relative paths, encoded control/slash tricks, userinfo and external origins. Reject unexpected Host/Origin rather than trusting arbitrary forwarded headers. Document required edge header scrubbing and fixed routing.
- Native machine API responses/auth regression-tested unchanged. A human without configured stack groups receives a clear forbidden result, not an invented admin role. Existing driver approval gates remain in force.

## Identity and discovery findings from the inspected deployment

- Existing machine `Claims::driver` prefers `preferred_username`, then `azp`, then `sub`. Do not reuse that fallback as browser human identity: two humans can share one client ID (`azp`). Bind browser ownership to the verified issuer and stable subject, with display name separate. The access token and ID token must identify the same subject; never infer identity from display text. Include a regression with two subjects under the same browser client. Preserve machine-driver semantics for existing callers.
- Read-only discovery from the existing driver provider succeeded; the redacted metadata is in `work/browser-oidc-discovery.json`. It advertises S256, authorization-code and refresh grants, but only `openid`, `sigiled-groups`, and `ak_proxy` scopes. Do not assume `profile`, `email`, or `offline_access` is provisioned. Make required scopes explicit and validate configured scope names without inventing availability.
- The existing provider is not proof that a suitable browser client or redirect URI is registered. Document the dedicated browser-client setup needed at release, never reuse the installed driver's client secret. Tests use only synthetic credentials. A compatible access token's issuer must be accepted by the downstream machine validators; configuration and live verification must cover this across Sigil, SDE, ADHD, Genie and memory.
- Authentik's current primary docs confirm refresh requires both requesting `offline_access` and provisioning its scope mapping. Document that optional browser-provider setup; absence of a refresh token is a supported finite session, not a reason to reuse credentials. Explicitly configure an asymmetric signing key: without one Authentik may use HS256 with the client secret, which is not this stack's RS256/JWKS contract. Register exact callback URLs, never rely on Authentik's first-use redirect registration.
- Bind cached JWT keys to trusted issuer/JWKS identity as well as kid, constrain algorithms, and bound metadata/JWKS response size/time/refresh behavior. The existing machine key store's kid-only cache should not weaken the exact browser issuer guarantee.
- Provider HTTP clients must reject redirects and keep client secrets/access/refresh credentials bound to configured endpoints. Do not inherit a generic redirect-following client for token exchange or future bearer adapters. Validate OIDC audience/authorized-party rules for multiple audiences and access-token hash if present, using the pinned verifier's supported primitives rather than an unsigned decode.
- The later memory service needs authenticated revision authorship. Extend the existing trusted `/auth/verify` result additively with stable verified issuer/subject/principal-kind metadata if necessary, while retaining its existing `caller`, service-policy behavior and headers. Never derive this metadata by decoding an unverified token or accepting a caller header. Browser actors and downstream curation can then bind to the same verified issuer/subject even when a username changes. Legacy/static authentication must remain explicitly legacy with no invented human subject. Document exact response fields for D1; do not add a generic impersonation endpoint.
- Primary references inspected 2026-09-10: [Authentik OAuth provider](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/), [OIDC ID token validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation), [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html). Use these to settle protocol details while keeping the implementation consistent with the actual pinned Rust dependencies.

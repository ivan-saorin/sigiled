## Requirements

- `Open IDE` operates as B1's authenticated actual human, enforcing CSRF/Origin and existing project/platform approval policy. It creates/resumes a workspace owned by that human, honors merge debt, and does not reuse or replace an unrelated agent's session. Repeated browser requests have a scoped idempotency key so a timeout does not create two workspaces. Recover the allocation identity from durable intent or the persisted A1 binding after process interruption; losing an in-memory response map must not silently allocate a second workspace. Return only safe session/readiness/launch metadata; all workspace and originator tokens stay server-side.
- Workspace and preview content use separate origins from Sigil/memory. Use a generation-specific hostname derived from the session ID, such as `{id}-g{generation}.ide.<domain>`, with all DNS labels <=63 bytes. Only exact registered active session/generation names resolve. Do not treat a slug in Host as permission or build an arbitrary upstream from it. No host port exposure; edge forwards wildcard IDE hostnames to this authenticated gateway.
- Preserve the full generation value across browser contracts. Use canonical decimal strings for browser-facing generation fields and parse them as bounded u64 values on the server; do not round-trip the machine API's numeric JSON through JavaScript numbers. Cover values above JavaScript's safe integer range. This is internal binding data, not a reason to expose implementation details in the visible interface.
- Host-only dashboard cookies cannot simply authenticate another origin. Implement a short-lived, one-use launch handoff bound to the authenticated browser session, actor, project, workspace ID, generation and exact destination origin. A fragment-carried ticket consumed by a same-origin POST is preferable to credentials in URL queries/logs. The launch page is platform-owned, uses no user HTML, no external scripts, no-referrer/no-store and a restrictive CSP. Consume the ticket atomically; replay/expiry/wrong origin/actor/generation all fail closed. Remove fragment/query before editor navigation. Never expose a workspace token or reusable IdP token as the launch ticket.
- IDE access uses its own Secure/HttpOnly/SameSite host-only cookie scoped to the exact generation origin. Validate ownership, lifecycle, generation, feature readiness and browser-session expiry on every HTTP request and WebSocket upgrade. Bind access lifetime to the real browser login, not a perpetual independent credential. Logout/revoke/close/recycle invalidates HTTP access and terminates established WebSockets promptly; the existing A1 session transition is the authority. Closing a tab does not close/merge a workspace.
- Reuse B1's real credential/expiry/refresh authority for an IDE grant; merely finding the parent session ID in a map is insufficient. The dashboard may be hidden while the user actively works in the IDE, so define parent-login idle activity deliberately and test that the active user can continue while absolute expiry/revocation still takes effect. Share the existing refresh serialization and cancellation guarantees instead of creating a second refresh path. Login activity and the C1 workspace idle lease are distinct: background WebSocket traffic must not become evidence of real workspace activity.
- Proxy only the known editor/helper target in the stored runtime binding. Strip spoofable identity, incoming Authorization, dashboard cookies and hop-by-hop headers; inject only the server-custodied session credential to the trusted helper. Bound upstream connect/read failures and provide actionable typed errors. Preserve required editor HTTP behavior, compression/ranges and WebSocket protocols. Do not leak helper/server secrets in errors or relay control cookies from untrusted upstreams. Avoid buffering unlimited editor uploads/downloads; use bounded streaming and sensible body limits.
- Preserve the editor's correct external authority and secure-context behavior through the helper: use the exact registered generation origin to construct trusted Host/Origin or forwarded metadata as required by the pinned provider, never a client-chosen forwarding value. Test actual resource/redirect/WebSocket URL behavior; an upstream loopback hostname leaking into URLs or origin checks is not a working IDE. The pinned provider route source inspected by the parent is cached at `work/code-server-pinned-vscode-route.txt` (official v4.136.2 source); folder/workspace query handling ultimately passes into VS Code. File-payload navigation still needs the requested provider integration smoke.
- Keep the platform launch page's restrictive CSP separate from the provider's necessary script/resource/worker behavior on its isolated origin. Preserve the dashboard's existing CSP. The real pinned-provider smoke should catch a shell that authenticates successfully but cannot load editor resources or workers because it inherited the dashboard boundary.
- Preview routes are a distinct authenticated origin and explicit session/port mapping. Validate numeric allowed ports and reject platform/agent/editor ports and unrelated network targets. The editor's built-in same-origin proxy must not allow project HTML to execute on the Sigil or editor access-cookie origin. If a compatibility feature cannot safely satisfy isolated previews yet, advertise it as unavailable with a precise reason; do not silently weaken origins.
- Workspace controls provide actual status, checkpoint/commit and deliberate finish. They use C1's durability interfaces and A1 close; failed checkpoint/push/merge preserves work and presents the recovery action. Do not claim saved browser buffers or merge on disconnect. Never expose a generic privileged `/exec` proxy to an unbound cookie session.
- Provide a narrow optional file target for D2's “Edit source” and the research handoff: a validated project-relative path plus optional bounded line/column, bound into the launch operation. The server builds the editor URL for its exact registered generation origin and `/workspace`; never accept arbitrary editor URLs or raw query payloads. Reject traversal, control characters and URI/authority injection, and report a missing/moved source truthfully. The [official code-server FAQ](https://coder.com/docs/code-server/FAQ#can-i-open-a-file-at-a-specific-line-from-a-url) documents a URL-encoded `payload` array with `openFile` and optional `gotoLineMode`, alongside the folder parameter. Verify this with the pinned provider before claiming file navigation works. This is navigation only, never an automatic file edit.
- Feature flags remain off until actual wildcard DNS/TLS, OIDC compatibility, provider bundle and repository protection readiness are configured. Supply exact edge rules and validation/rollback steps; do not assume a new wildcard certificate/DNS entry exists. Existing `/sigiled/*` and returned workspace-machine endpoints remain compatible.

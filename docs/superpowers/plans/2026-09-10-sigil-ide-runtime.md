## Required behavior

1. Build a pinned platform-managed IDE layer over the resolved **project** image. Cache by base image digest, provider version and platform helper revision, not merely a mutable tag. Preserve project toolchain, user, entrypoint/CMD, workspace bootstrap and compiled vm-base extensions. Copying a generic replacement vm-base binary over a project's existing one can erase extensions: avoid that. A small independent companion/helper launched after bootstrap is acceptable. Do not install/update every project repo by hand. Heavy code-server processes start only on demand; existing agent sessions keep their current behavior.
2. Authenticate all helper/control traffic using session-generation credentials held by the control plane; do not publish editor/helper ports to the host. code-server can use external authentication only behind the authenticated gateway; bind its direct listener to loopback inside the workspace and route through an authenticated companion if necessary. Disable its generic same-origin preview proxy until C2 supplies explicit isolated-origin preview mappings. No arbitrary upstream URLs or host filesystem mounts from project metadata.
3. Readiness is explicit: inherited desired capability, provider/image build pending, incompatible image, process starting/ready/stopped/failed, and safe last error. Bounded readiness probes and log tails must not leak tokens or environment credentials. Store resolved image/provider/generation in the A1 binding/projection. Open/recycle/reaper/close all use the recorded binding and preserve A1 failure guarantees. Builds/probes must not hold unrelated project/session locks longer than needed; reuse lifecycle serialization and keep late task results from overwriting a newer generation.
4. Full editor features include files/search/terminal/Git/extensions with project tools. Persist editor settings/extensions in an explicitly named operator profile volume, isolated from other operators; avoid concurrent writers sharing one editor SQLite/profile instance. Session-specific live state and IPC paths with reusable operator preferences are acceptable. No unsaved browser-buffer durability promise.
5. Expose authenticated machine/provider operations for IDE start/status/stop or an equivalent narrow interface for C2. Require actor ownership/admin, permitted session lifecycle/generation and feature readiness. Return safe metadata only. A browser disconnect is not a merge or finish. Do not stop an agent workspace when an independent human IDE starts.
6. Git durability states are separate: saved to disk, dirty, committed, pushed/checkpointed, merged. Existing Sigil commit behavior pushes. Terminal/extension-created commits must be detected and pushed to the **session branch only** by a supervised, bounded synchronization loop. If checkout/remote differs from the expected session branch, pause synchronization with an actionable error rather than switching/resetting it. Never force push; never push master from the helper. Serialize against repository Git operations using a deliberate shared mechanism; retain failed work on local commit/push errors. A checkpoint commits dirty work with clear metadata and pushes. A finish action eventually calls normal Sigil close only after successful checkpoint. Periodic checks alone do not keep a workspace alive.
7. A repo-level rule protecting master from direct terminal/Git-extension pushes is a production readiness prerequisite, because existing workspaces hold a write deploy key. Do not pretend a local hook is enforcement. Verify an actual configured repository policy through an available trusted read interface or keep the production full-write IDE feature gated with a specific setup reason. Do not silently rewrite existing repository rules. Document exact external prerequisite and which actor can still perform Sigil's normal merge push.
8. Account for actual editor/terminal activity, not health, filesystem polling, autosave synchronization or an abandoned WebSocket alone. A small bundled editor extension may report real user edit/save/selection/command activity to the authenticated companion. Define the observable limits honestly and test that background-only traffic does not extend the idle lease. Avoid reaping during a known running user command/checkpoint. Activity reporting must be bound to this session/generation.
9. Implement stop/restart supervision and recovery without arbitrary process killing or reusing another session's state. Failed companion/editor startup cleans up only its own processes and keeps workspace files. Profile retention on finish/reap is separate from project branch persistence. Raw workspace/IDE credentials never go to dashboard JSON.

## Verification

Repository-policy implementation finding: inspected `sigiledd/src/github.rs` is cached in `work/sigiled-github-pre-ide.txt`. The control plane already has a host-held GitHub PAT for repo creation/deploy-key registration; it is not in workspaces and must stay there. Both current workspace push and `Runtime::push` use the same per-project write deploy key. Merely adding a branch rule that rejects that key would also reject normal close/merge. Read-only GitHub policy inspection can use the existing trusted client with proper bounds/redirect handling, but the production setup must distinguish the allowed control-plane merge identity from the workspace key. Do not mark protected/ready from a single boolean, an operator-provided manifest field, or presence of any unrelated branch rule. If adding a narrowly configured host-only merge transport is necessary, keep its secret out of command arguments, Git remotes, subprocess output and the workspace, preserve the old path while the feature is disabled, and test failed merge preservation. Do not mutate live repository policies in this task.

Primary references inspected: [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [rules API](https://docs.github.com/en/rest/repos/rules). Active rules and bypass actors both matter; `DeployKey` can be a bypass class, so two deploy keys are not automatically distinct policy principals. Private-repository protection also depends on the account plan. Report inability to inspect/enforce explicitly instead of claiming it from a local hook.

Additional policy-inspection details verified against the official rules API on 2026-09-10: `GET /repos/{owner}/{repo}/rules/branches/master` returns applicable active rules across levels, with paginated results; disabled/evaluate rules do not establish protection. Read the corresponding ruleset details including parent rules. GitHub returns `bypass_actors` only to callers with write access to that ruleset: an omitted field is unknown, not an empty bypass list. The current schema supports `User` with an actor ID and `DeployKey` as an ID-less class; a host PAT's verified actor may therefore provide a distinct merge principal, but do not assume the configured token has that authority. Bound all pages/requests and report incomplete/unknown policy instead of granting readiness. A conservative supported policy subset is acceptable with a precise reason when other rule combinations cannot be proven safe; do not advertise universal GitHub-policy interpretation.

Git coordination must distinguish platform operations from arbitrary terminal processes. A cooperative lock between vm-base and the companion does not make an unrelated terminal command acquire it. Preserve existing Git lock files, use normal non-forced Git behavior, recheck expected branch/remote/HEAD around platform checkpoint/synchronization, and return a recoverable concurrent-change condition when necessary. Never reset, delete a pre-existing Git lock, or claim comprehensive terminal serialization from a wrapper that the user can bypass. Replacing the existing extended vm-base with an unrelated generic build remains prohibited.

Use actual temporary Git repositories/bare remotes for checkpoint, terminal-created commit, divergent remote, branch switch, failed push and retry. Use controllable fake editor processes for start/stop/readiness/restart/generation/activity tests; no production Docker. Test immutable image-key generation, checksum verification, inherited old manifests, preserved entrypoint/toolchain/extensions, unsupported image errors and independent same-project sessions. Verify no published ports and no wrong-session cleanup with A1 fake runtime. If the sealed container can run the pinned standalone provider, a bounded local `--version`/health smoke test is useful; it is not a deployed browser acceptance test.

Test first, run appropriate focused/full regression, document exact results and rollout prerequisites. Update contract/runbook/log-operativo, review diff for binaries/scratch, commit coherent source changes. Do not claim the browser IDE is deployed or end-to-end verified until C2 and actual edge/SSO rollout pass.
